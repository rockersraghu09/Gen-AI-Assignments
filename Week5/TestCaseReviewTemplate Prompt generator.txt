(I) INSTRUCTIONS / DIRECTIVE
You must review the provided test case for quality and then produce:
1) A list of issues (grouped by Completeness, Clarity, Best Practices)
2) Suggestions for improvement (actionable, specific, prioritized)
3) A rewritten improved version of the test case (fully executable, deterministic, and aligned to best practices)

Evaluation goals:
- Ensure the test case can be executed successfully by a new QA engineer without any external assumptions.
- Ensure each step is unambiguous, atomic (single action per step), and verifiable.
- Ensure expected results are measurable/observable and map to steps.
- Ensure prerequisites, environment, and test data are sufficient and realistic.
- Ensure coverage includes relevant negative paths and edge cases (when applicable).
- Ensure the test case is structured, consistent, and maintainable for reuse/automation.

Review categories (you must evaluate all):
A) Completeness
   - Missing required fields (ID, title, objective, preconditions, environment, test data, steps, expected results, postconditions)
   - Missing setup/configuration/roles/permissions
   - Missing validation points/assertions
   - Missing cleanup/postconditions when state changes
   - Missing scenario variations: negative, boundary, edge cases where relevant
B) Clarity
   - Ambiguous language (“verify”, “check”, “ensure”) without explicit verifiable criteria
   - Steps combine multiple actions
   - Steps depend on unspecified prior knowledge or hidden assumptions
   - Inconsistent terminology or unclear UI element names
   - Expected results vague or not tied to a step
C) Best Practices
   - Test case tries to cover too many objectives; should be single-purpose
   - Preconditions contain steps that should be setup, or vice versa
   - Non-deterministic instructions (“wait some time”, “may”, “sometimes”)
   - Lacks traceability (requirement/user story reference) when provided
   - Doesn’t separate test data from steps
   - No mention of logs/telemetry checks when relevant and available
   - Missing accessibility/security/performance notes when the scenario suggests it

Severity rules (use these consistently):
- Critical: Prevents execution or makes expected result unverifiable
- Major: Likely to cause inconsistent execution or misses key validation
- Minor: Readability/formatting improvements
- Suggestion: Optional enhancements (maintainability, automation readiness)

Quality rules:
- Do NOT invent product features not present in the test case.
- If the test case lacks context needed to be complete, call it out explicitly and propose the minimal questions or assumptions required.
- Prefer “ask to clarify” as an issue + suggestion rather than hallucinating details.

(C) CONTEXT
You are reviewing test cases used in professional software delivery.
The outputs must be suitable for:
- Peer review in a QA team
- Execution by manual testers
- Future automation (readability, determinism, stable selectors/validation points)

Assume test cases may come in any format (bullet list, table, free text).
Your job is to normalize them into a structured, best-practice test case.

Common best-practice structure (target structure for the improved test case):
- Test Case ID
- Title
- Objective
- Preconditions
- Test Data
- Environment
- Steps (numbered, atomic actions)
- Expected Results (per step, verifiable)
- Postconditions / Cleanup
- Notes (risks, observability, automation hooks, traceability)
